In Entity Framework (EF), there are mainly three types of loading for related data (navigation properties):

Eager Loading
Lazy Loading
Explicit Loading
1. Eager Loading

Eager loading loads the related data together with the main entity in a single query (or related queries).

You use the Include() method.

Example:

var country = db.Countries
                .Include(c => c.States)
                .FirstOrDefault();

Here:

Country data is loaded.
Related States data is loaded immediately.

Generated SQL is similar to:

SELECT *
FROM Country
LEFT JOIN State
ON Country.CountryId = State.CountryId
When to use:
You know you need related data.
Avoids multiple database calls.

Example:

foreach(var state in country.States)
{
    Console.WriteLine(state.StateName);
}

No extra database query is fired.

2. Lazy Loading

Lazy loading loads related data only when you access the navigation property.

Example:

var country = db.Countries.FirstOrDefault();

var states = country.States;

When this line executes:

country.States

EF automatically sends a query to get states.

For lazy loading:

Navigation properties must usually be virtual.

Example:

public virtual ICollection<State> States { get; set; }
Enable lazy loading in EF Core:

Install:

Microsoft.EntityFrameworkCore.Proxies

Enable:

optionsBuilder
.UseLazyLoadingProxies()
.UseSqlServer(connectionString);
Problem:

It can create the N+1 query problem.

Example:

var countries = db.Countries.ToList();

foreach(var country in countries)
{
    Console.WriteLine(country.States.Count);
}

If there are 100 countries:

1 query for countries
100 queries for states

Total = 101 queries.

3. Explicit Loading

Explicit loading means you manually tell EF when to load related data.

Example:

var country = db.Countries.First();

db.Entry(country)
  .Collection(c => c.States)
  .Load();

Now states are loaded.

You decide when the database call happens.

When to use:
You don't always need related data.
You want control over when loading occurs.
Comparison
Type	Loads When	Method	Control
Eager Loading	Immediately	Include()	Low
Lazy Loading	When property is accessed	virtual navigation property	Automatic
Explicit Loading	When you manually request	.Load()	High
In Database First

Your generated class:

public virtual ICollection<State> States { get; set; }

supports Lazy Loading if configured, but you can still use:

.Include(c => c.States)

for eager loading or:

.Entry(country).Collection(c => c.States).Load();

for explicit loading.

So, in EF Core and EF 6, the three standard loading types are:

1. Eager Loading
2. Lazy Loading
3. Explicit Loading

When should you use ADO.NET?

Use ADO.NET when:

You need maximum performance.
You're executing complex stored procedures.
You're working with bulk data imports/exports.
You need fine-grained control over SQL execution.

Example:

SqlBulkCopy

is available through ADO.NET for fast bulk inserts.

When should you use EF?

Use EF when:

Building ASP.NET Core applications.
Developing CRUD applications.
Working with many related tables.
You want faster development and easier maintenance.

This is the most common choice for modern .NET business applications.



ADO.NET is a low-level data access technology where developers write SQL queries, manage connections, and map data manually.

Entity Framework is an ORM built on top of ADO.NET. It allows developers to work with C# objects and LINQ instead of writing most SQL manually. EF provides features such as change tracking, relationship management, lazy/eager loading, and automatic CRUD operations, making development faster and code easier to maintain.

Which should you learn?

Since you're already learning Entity Framework Database First, it's still important to know the basics of ADO.NET because:

EF internally uses ADO.NET.
Many interviews ask about both.
Some advanced scenarios (like SqlBulkCopy or certain stored procedure patterns) still require ADO.NET.

A strong .NET developer is comfortable with both, even if EF is the primary tool used day to day.

In .NET (especially for APIs using JWT authentication),
Access Tokens and Refresh Tokens are commonly used together to provide
 secure authentication while minimizing the need for users to log in repeatedly.
 
An Access Token is a short-lived token that a client (web app, mobile app, etc.) 
sends with API requests to prove the user's identity.
 Characteristics
Usually a JWT (JSON Web Token).
Contains user information (claims).
Short expiration time (e.g., 15–60 minutes).
Used to access protected API endpoints.

A Refresh Token is a long-lived token used to obtain a new access token when the old one expires.
 Characteristics
Usually stored in a database.
Longer expiration (days, weeks, or months).
Never used to access APIs directly.
Used only for generating new access tokens.

A JWT (JSON Web Token) is a compact, secure way to transmit information between a client (browser/mobile app) and a server.
It's commonly used for authentication and authorization in web applications.

JWT Flow

Here's the typical flow:

+--------+            +-----------+
| Client |            |  Server   |
+--------+            +-----------+
     |                      |
1. Login (username/password)
     |--------------------->|
     |                      |
2. Validate credentials
     |<---------------------|
     |   JWT Token          |
     |
3. Store Token
(Local Storage/Session Storage/Cookie)
     |
4. API Request
Authorization: Bearer <JWT>
     |--------------------->|
     |                      |
5. Verify JWT
     |                      |
6. Return Protected Data
     |<---------------------|
Step 1: User Logs In

The user sends their credentials to the server.

Request

POST /login

{
  "email": "john@example.com",
  "password": "password123"
}
Step 2: Server Validates User

The server checks the username and password against the database.

If valid, it creates a JWT.

Step 3: Server Creates JWT

A JWT has three parts separated by dots (.):

xxxxx.yyyyy.zzzzz
1. Header

Contains token metadata.

{
  "alg": "HS256",
  "typ": "JWT"
}

After Base64 encoding:

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9
2. Payload

Contains claims (data).

{
  "id": 101,
  "name": "John",
  "role": "Admin",
  "exp": 1750000000
}

Example claims:

User ID
Username
Role
Expiration time (exp)
Issued at (iat)
3. Signature

The server signs the token using a secret key.

HMACSHA256(
   Header + "." + Payload,
   SecretKey
)

Final JWT:

Header.Payload.Signature

Example:

eyJhbGc...eyJpZCI...AbCdEf123XYZ
Step 4: Client Stores JWT

Common storage options:

HttpOnly Cookie (recommended for browser apps)
Local Storage
Session Storage
Step 5: Client Sends JWT

Every protected request includes the token.

GET /profile

Authorization: Bearer eyJhbGc...
Step 6: Server Verifies JWT

The server:

Extracts the token.
Verifies the signature using the secret (or public key for asymmetric algorithms like RS256).
Checks expiration (exp).
Reads the payload.

If valid:

Allow Request

Otherwise:

401 Unauthorized
JWT Structure
Header
{
 "alg":"HS256",
 "typ":"JWT"
}

        ↓

Payload
{
 "id":101,
 "role":"Admin",
 "exp":1750000000
}

        ↓

Signature
HMACSHA256(
 Header + Payload,
 SecretKey
)
Example in Node.js

Generate a token:

const jwt = require('jsonwebtoken');

const token = jwt.sign(
  {
    id: 1,
    role: 'Admin'
  },
  'mySecretKey',
  {
    expiresIn: '1h'
  }
);

console.log(token);

Verify a token:

const decoded = jwt.verify(token, 'mySecretKey');

console.log(decoded);

Create an HTTP interceptor:

intercept(req: HttpRequest<any>, next: HttpHandler) {

  const token = localStorage.getItem('token');

  if (token) {
    req = req.clone({
      setHeaders: {
        Authorization: `Bearer ${token}`
      }
    });
  }

  return next.handle(req);
}

Why Use JWT?

Advantages:

Stateless authentication (server doesn't need to store session data)
Works well across different domains and services
Compact and easy to send in HTTP headers
Suitable for REST APIs and microservices

Limitations:

A JWT cannot usually be invalidated before it expires unless you add a revocation or blacklist mechanism.
If stored insecurely (for example, in localStorage), it can be stolen by malicious scripts if your application has an XSS vulnerability.
Tokens should contain only necessary information; avoid storing sensitive data because the payload is only Base64-encoded, not encrypted.
